2. The Urban Parking Concurrency Problem

Why naive implementations fail under real-world multi-worker loads

❌ The Flawed Naive Approach

  • Read-Then-Write Race Condition: User A queries slot status (sees AVAILABLE). At the same millisecond, User B queries same slot (sees AVAILABLE). Both submit bookings; both are confirmed. Result: Double-booking disaster.
  • In-Memory Locks Fail Across Workers: Using threading.Lock() in Python only protects threads inside a single OS process. In production Gunicorn with 2–4 worker processes, memory is NOT shared, making in-memory locks completely useless.
  • Frontend Button Disabling Is Ineffective: Client-side UI disables can be bypassed by API scripts, network retries, or concurrent mobile apps.

✅ Our Multi-Layered Concurrency Defense

  • Database Row-Level Locking (PostgreSQL): Uses with_for_update() to acquire an exclusive row-level lock on the target slot. Competing transactions wait until the first commits or are immediately rejected.
  • Atomic Conditional Updates (SQLite & Postgres): UPDATE parking_slots SET status = 'OCCUPIED' WHERE id = ? AND status = 'AVAILABLE'. SQLite guarantees atomic execution: exactly one thread gets rowcount == 1; competing threads get rowcount == 0 and are safely aborted.
  • Physical Schema Partial Unique Index: CREATE UNIQUE INDEX idx_active_slot_booking ON bookings(slot_id) WHERE status = 'ACTIVE'. Even if application code failed, the database engine physically rejects duplicate active reservations.

3. College Project Review & Viva Preparation

Direct answers to core questions frequently asked by academic evaluation committees

Examiner Q&A

Q1: How do you prove your system prevents race conditions?

We have written automated stress tests in tests/test_concurrency.py using Python's concurrent.futures.ThreadPoolExecutor with a threading.Barrier. We launch 12 parallel threads that hit the booking endpoint at the exact same millisecond for the same slot. In 100% of test runs, exactly 1 thread succeeds (HTTP 201), and 11 threads are rejected (HTTP 409 Conflict), with exactly 1 active record stored in the database.

Q2: How does the surge pricing algorithm work? Is it simulated or AI-based?

The pricing model is an occupancy-elastic algorithmic function, NOT an unverified machine learning claim. It evaluates real-time bay occupancy: Occupancy % = (Occupied / Total) × 100. When occupancy crosses defined thresholds (<50%, 50–74%, 75–89%, ≥90%), a transparent multiplier (1.0x to 2.0x) is applied to the zone base rate. It is strictly bounded by anti-gouging minimum (1.0x) and maximum (2.0x) caps.

Q3: How does the application handle SQLite in development vs PostgreSQL in production?

SQLAlchemy ORM provides database abstraction. In development, SQLite is configured with WAL (Write-Ahead Logging) mode and a 15-second busy timeout. In production on PostgreSQL (Render/Railway), the allocation engine dynamically detects the PostgreSQL dialect and applies row-level locking via with_for_update(). Both databases enforce the identical partial unique constraint idx_active_slot_booking.

4. System Limitations & Future Roadmap
